# The four landed pre-PM stages become M1–M4 and the plan's stages shift to M5–M8

## Context

`docs/history/**` holds the frozen record of the plan that preceded `docs/pm/`: Stages 1 and 2 in `stages-1-2.md`, Stage 3 in `stages-3.md`, Stage 4 in `stages-4.md`, and the 2026-09-17 plan review in `retrospective-2026-09-17.md`. The PM tree held only PLAN stages 5–8, as milestones M1–M4, so four landed stages existed with no milestone, task, retro or decision record in the plan. Their task ids could not follow the plan's hundred-digit convention: that digit encodes the stage a task was fixed in, and Stage 1's tasks were fixed as `1.x`. Reusing M1–M4 for the landed stages would therefore also have renamed the plan's sixteen M1 tasks for no reason other than a collision.

## Decision

Milestones: M1 = Stage 1, Initialization; M2 = Stage 2, Data points; M3 = Stage 3, Static build framework; M4 = Stage 4, Frontend build — all four `completed`, dated 2026-09-14, with the retros `RETRO-2026-09-17-001` … `RETRO-2026-09-17-004` reconstructed from the frozen history. The plan's stages 5–8 shifted up by four and stay M5–M8, `in_progress` … `backlog`, and every task id is unchanged (`UI-501` … `DATA-802`), because the hundred digit is the stage label it keeps.

Task ids in the migrated milestones are `<PREFIX>-<stage><NN>`: the stage's own label `N.M` becomes `-N` plus a two-digit sequence, and a lettered label keeps its letter (`1.4b` → `DATA-104b`, `3.3b` → `APP-303b`). No legacy label is a task name, and no migrated task text was enriched or rewritten: each task document carries the stage's own task text, and the stage's acceptance, handover contract and session records live in its milestone README. The owner decisions those sessions took are extracted as `DEC-2026-09-14-001` … `-012`, with the stage's own numbers and rejected alternatives preserved verbatim; `pre` is empty everywhere because the stages' order came from their own task lists, not from recorded prerequisites.

## Consequences

`docs/pm/plan.yml` now lists M1–M4 as completed ahead of M5 at `in_progress`, so a session reads the landed history before the live stage. `docs/history/**` is unchanged and remains the authoritative record of those four stages; the stage labels (`5.2`, `1.4b`, `3.3b`) survive inside quoted task text, session records and gate evidence as history, but never as a task name. Every live cross-reference from M5–M8 to the old M1–M4 was retargeted to M5–M8 before the shift landed, and the review's own "5.x" references are read through the canonical-id mapping above. The ids M1–M4 are now owned by the landed stages and are no longer available to the plan; the next stage after M8 takes M9.
